# Windows production transactional authority schema and initialization

## Scope and decision

This milestone defines the production database contract that follows
[architecture 78](78-windows-authority-provisioning.md) and makes the
transactional authority in [architecture 77](77-windows-transactional-capture-authority.md)
recognizable as an executable production authority. It is a design milestone
only. It does not implement a database initializer, change the Architecture-77
fixture, add a broker, read credentials, call a provider, launch a child,
schedule work, or enable live trading.

The fixed security boundary remains unchanged:

- the database is only `F:\AITradingBot\Authority\authority.sqlite3` and its
  pre-created `authority.sqlite3-journal`;
- Architecture-78 path, final-handle, owner, DACL, reparse, local-NTFS,
  bootstrap, signature, SID, and policy checks happen before SQLite access;
- the database uses one local main database, `PERSIST`, `synchronous=FULL`,
  `foreign_keys=ON`, and `trusted_schema=OFF` for every production
  connection where the reviewed SQLite build supports the setting;
- there is no `ATTACH`, `VACUUM`, fallback database, automatic repair, or
  automatic migration; and
- the database remains an auditable paper/market-data capture authority, not a
  live-order or credential authority.

The approved initialized state introduced here is
`INITIALIZED_SUPPORTED`. An initialized database is accepted only when its
exact schema, immutable metadata, migration evidence, signed-bootstrap
reconciliation, and SQLite integrity all pass.

## 1. Canonical production schema artifact

### 1.1 Location and stable identity

The one canonical production SQL artifact will be packaged at:

```text
src/trading_bot/runtime/schema/windows_transactional_authority_v1.sql
```

The package build must include this resource and the initializer/validator
must load it through the package resource API. A current-working-directory
path, environment variable, CLI path, or database value cannot select a
schema artifact.

Its stable identity is:

```text
schema_id       = windows-transactional-authority-schema/v1
schema_version  = 1
```

The artifact is an ordered UTF-8 SQL byte stream with no BOM, LF line endings,
ASCII semicolon statement termination, and exactly one final LF. The exact
bytes, including comments and whitespace, are part of the artifact identity.
The SHA-256 of those bytes is the production `production_schema_digest`:

- code/release material stores the expected digest as 32 raw bytes or its
  lowercase 64-character hexadecimal form;
- `authority_metadata.production_schema_digest` stores the 32 raw bytes; and
- canonical JSON represents that value as lowercase hexadecimal text.

The database file, SQLite page bytes, journal bytes, root pages, rowids, and
metadata values are not inputs to this digest. This avoids circularity and
keeps the digest an identity of the reviewed schema source rather than an
identity of one mutable database instance.

The artifact includes the Architecture-77 relational authority surface: the
ten tables `authority_metadata`, `schema_migrations`, `sessions`, `attempts`,
`provider_call_claims`, `launch_reservations`, `launch_executions`,
`terminals`, `session_selections`, and `manual_recoveries`; the Architecture-77
triggers; no views; and no caller-created indexes. Primary-key and UNIQUE
indexes generated by SQLite are part of the conformance result. The exact
object definitions, not this summary, are normative once the artifact is
created.

The production artifact is an audited v1 derivative of the fixture, not an
unreviewed copy. The deliberate production changes are:

1. exact v1 production schema identity fields and checks are added to
   `authority_metadata`;
2. `authority_metadata.bootstrap_schema` is exact `1`, rather than merely
   positive;
3. `schema_migrations.schema_version` and its migration policy are exact v1
   values, rather than any positive version;
4. initializer validation gives `metadata_json` and `migration_json` exact
   semantic contracts; and
5. cryptographic digest checks move out of schema-controlled SQL execution.
   Production v1 has no dependency on an application-defined `sha256()` SQL
   function and executes with `trusted_schema=OFF`.

The production SQL artifact must not silently remove the Architecture-77
lineage, immutable-row, evidence-pair, state-machine, or recovery triggers.
Any trigger or constraint change is a schema change and therefore changes the
artifact digest and requires a new reviewed schema identity.

### 1.2 Fixture relationship and divergence control

The implementation correction makes
`src/trading_bot/runtime/schema/windows_transactional_authority_v1.sql` the
only checked-in full authority SQL source. The Architecture-77 executable
harness loads those exact bytes through the public package/resource boundary,
materializes them with `trusted_schema=OFF`, and runs its behavioral suite
against that database. The former
`tests/fixtures/transactional_authority_schema.sql` copy is removed; no
compatibility loader contains independent schema bytes.

The conformance tests compare the materialized schema manifest to the approved
golden vector and include a regression that the harness bytes equal the
packaged resource. The only intentional behavioral-harness differences are
the production v1 metadata/migration contract and the relocation of digest
checks from SQL triggers to Python mutation/read-only validation boundaries.

Production v1 inserts `schema_version=1`; the migration golden vector was
regenerated for that version. The session/attempt/claim/reservation/execution/
terminal identity contracts and canonical bytes remain unchanged. CI must fail
if a second full SQL schema or an unapproved artifact digest is introduced.

### 1.3 Digest responsibility and complete fixture audit

The Architecture-77 fixture contains 50 `sha256()` call sites across these
18 triggers: `authority_metadata_before_insert` (1),
`schema_migrations_before_insert` (1), `sessions_before_insert` (1),
`attempts_before_insert` (3), `provider_call_claims_before_insert` (4),
`launch_reservations_before_insert` (1),
`launch_reservations_process_intent_append_only` (1),
`launch_reservations_failure_evidence_guard` (2),
`launch_reservations_state_guard` (9),
`launch_executions_before_insert` (3),
`launch_executions_parent_policy_before_insert` (1),
`launch_executions_phase_guard` (3),
`launch_executions_resume_intent_append_only` (1),
`launch_executions_post_resume_append_only` (1),
`launch_executions_cleanup_append_only` (1), `terminals_before_insert` (3),
`session_selections_before_insert` (1), and `manual_recoveries_before_insert`
(13).

The audit classification is:

| Fixture use | Count | Invariant and production treatment |
| --- | ---: | --- |
| Direct or append-only `bytes`/digest comparisons for metadata, migration, request, allocation, claim, reservation, process, execution, terminal, selection, and recovery evidence | 21 | Cryptographic byte/digest equality. The reviewed Python transaction service computes SHA-256 over the exact canonical bytes before insertion/update, inserts the bytes and raw 32-byte digest in the same transaction, and read-only validation recomputes every required digest before authority use. Production SQL retains BLOB length, NULL-pair, NOT NULL, immutable, and state constraints but does not recompute the digest. |
| Digest predicates inside claim admission, reservation/execution phase guards, terminal admission, and recovery action guards | 29 | Cryptographic validity used as a prerequisite for relational/state-machine admission. Production native triggers retain the normalized lineage, state, timestamp, uniqueness, immutability, and recovery predicates. The reviewed service must additionally validate every referenced evidence pair before dependent mutation; read-only validation does the same. Direct arbitrary SQL under the trusted Trading-token assumption is not treated as a defended service path. |
| UUID5 identity derivation | 0 | No fixture `sha256()` call derives an authority identity. Existing Architecture-77 UUID5 framing and identity ownership are unchanged. |

The 29 relational uses are not silently discarded: their non-cryptographic
state and lineage conditions remain native SQLite enforcement, while their
cryptographic precondition moves to the service/validation layer. A malformed
or mismatched stored digest therefore blocks a reviewed authority operation
before its dependent mutation, even though SQLite v1 no longer calls a custom
hash function from a trigger.

This is an intentional trust-boundary correction. Architecture 77 already
assumes the dedicated Trading token is trusted; SQLite constraints do not
protect against arbitrary malicious SQL from code that fully controls that
token. The service boundary, exact schema fingerprint, immutable evidence
triggers, and fail-closed validation remain mandatory.

## 2. Exact schema validation and fingerprint

No table-name or row-count check is sufficient. Installed validation uses two
independent layers:

1. exact artifact identity, by hashing the code-owned SQL resource and
   comparing it with the code-owned expected digest and the immutable metadata
   column; and
2. exact materialized-schema conformance, by comparing the installed database
   with a schema manifest materialized from the exact artifact using the
   reviewed SQLite build.

### 2.1 Materialized schema manifest

The validator creates a disposable in-memory SQLite connection with the same
reviewed SQLite build, establishes `trusted_schema=OFF`, executes the
canonical artifact without registering any application-defined SQL function,
and derives an internal `schema-manifest/v1`. It derives the same manifest
read-only from the installed database. The manifest is compared as structured
data, not as a database file digest.

The manifest contains:

- every non-engine `sqlite_schema` row, sorted by `(type, name, tbl_name)`,
  with exact `type`, `name`, `tbl_name`, and stored `sql` text; `rootpage` is
  deliberately excluded because it is an allocation detail;
- the complete `PRAGMA table_xinfo` result for every production table,
  including column order, names, declared types, NOT NULL flags, default SQL,
  primary-key position, generated-column flags, and hidden-column flags;
- the complete `PRAGMA index_list` and `PRAGMA index_xinfo` results for every
  production table, including UNIQUE/PRIMARY KEY origin, partial status,
  column order, collations, sort order, and key-column flags; and
- the complete `PRAGMA foreign_key_list` result for every production table,
  including referenced table/columns and update, delete, and match actions.

The manifest contains no root pages, rowids, timestamps, paths, platform
aliases, or database content. It has no views or virtual tables in the v1
expected set. SQLite-generated `sqlite_autoindex_*` structures are checked
through the index manifest; unexpected `sqlite_stat*`, `sqlite_sequence`,
virtual-table, or other non-expected structures fail closed. An unexpected
application object is never ignored merely because its name begins with
`sqlite_`.

SQL text is compared exactly as stored by the reviewed SQLite build. No
whitespace, keyword, CHECK expression, trigger-body, or foreign-key clause is
normalized. This intentionally rejects modified triggers, altered CHECK
constraints, changed foreign keys, and changed index definitions. `rootpage`
and index-list sequence numbers are the only allocation/order values omitted
from the comparison. A different SQLite build that materializes a different
schema representation fails closed; production acceptance must pin the build
and its VFS rather than broadening the comparison.

The manifest is an internal validation value, not a persisted database digest.
Persisting a digest of a manifest containing the metadata row would create an
unnecessary self-reference. The persisted schema identity is the digest of
the canonical SQL artifact; the manifest proves that the installed schema is
the exact reviewed materialization of that artifact.

### 2.2 Validation order and failure classes

After Architecture-78 trust is established and before any mutable connection
is opened, installed validation performs, in order:

1. require the paired fixed database and persistent journal;
2. open the exact database with SQLite `mode=ro`, with no URI fallback;
3. establish and read back `trusted_schema=OFF` before reading or executing
   any persistent schema-controlled SQL;
4. require one `main` database and no attachments, and compare the exact
   final database path;
5. read `sqlite_schema`, the manifest PRAGMAs, `PRAGMA integrity_check`, and
   `PRAGMA foreign_key_check`;
6. compare the exact materialized schema manifest and artifact digest;
7. read exactly one immutable metadata row and exactly one v1 migration row;
8. validate canonical metadata/migration bytes and their SHA-256 digests;
9. reconcile every bootstrap-bound fact; and
10. return sanitized immutable evidence only after all checks pass.

The validator does not set `journal_mode`, `synchronous`, or
`foreign_keys`; it establishes and reads back `trusted_schema=OFF` where the
reviewed build supports it. It does not run DDL, attach another database,
vacuum, repair, rewrite rows, or clear the persistent journal. A read-only
validation error is terminal for that invocation and never becomes an
automatic repair path.

### 2.3 Connection-local SQLite security contract

Every production authority connection has this connection-local contract:

| Setting | Required value | Scope and rationale |
| --- | --- | --- |
| `foreign_keys` | `ON` / readback `1` | Required for relational authority enforcement on administrator and runtime writable connections. |
| `journal_mode` | `PERSIST` / readback `persist` | Required for the fixed database/journal durability contract on writable connections. |
| `synchronous` | `FULL` / readback `2` | Required for the reviewed runtime durability contract on writable connections. |
| `trusted_schema` | `OFF` / readback `0` | Required on initializer, runtime, and supported read-only validation connections so persistent schema code cannot call application-defined functions. |

`trusted_schema` is not database mutation. It is a connection-local SQLite
security setting and must be established before schema-controlled SQL can be
prepared or executed. On Python 3.12 or newer, the preferred standard-library
path is the public `Connection.setconfig()` with
`sqlite3.SQLITE_DBCONFIG_TRUSTED_SCHEMA` and value `0`, followed by an explicit
`PRAGMA trusted_schema` readback. A public `PRAGMA trusted_schema=OFF` write may
be used only when the supported standard-library/SQLite combination exposes
the pragma but not the public config constant. Private APIs, ctypes SQLite
bindings, alternate drivers, extensions, and loadable extensions are not part
of this milestone.

The supported production build is one explicitly published
`sqlite-authority/v1` build manifest containing the exact SQLite library
version/build, compile options, VFS, and successful `trusted_schema=OFF`
behavior. A build that cannot establish or read back `trusted_schema=OFF`, or
that cannot execute the production artifact under that setting, is
`INITIALIZED_UNSUPPORTED`/runtime-invalid and fails closed. There is no
fallback to `trusted_schema=ON`. Until that reviewed Windows build manifest
is published, production remains NO-GO; a broad “any SQLite 3.x” claim is not
made.

`trusted_schema=OFF` does not make a hostile database safe by itself. Exact
filesystem/bootstrap trust, exact schema materialization, immutable metadata,
Python digest verification, integrity checks, and unexpected-state rejection
remain mandatory.

## 3. Production `authority_metadata` v1 contract

The row remains a singleton, with `singleton_key=1`, a primary key on
`authority_epoch_id`, a uniqueness rule on `machine_authority_id`, and
immutable/undeletable triggers. It contains no secret, credential, private
key, token, provider response, or arbitrary exception text.

The production columns are the Architecture-77 fields plus the five explicit
schema/encoding/initialization fields below. All fixed text values are checked
by the production DDL and rechecked by the read-only validator.

| Column | Type and exact meaning |
| --- | --- |
| `authority_epoch_id` | Canonical lowercase UUID text; exact signed epoch fact and primary key. |
| `machine_authority_id` | Canonical lowercase UUID text; exact signed machine fact and unique. |
| `bootstrap_schema` | Integer, exact `1`; copied from the signed bootstrap. |
| `bootstrap_generation` | Positive integer; copied from the signed bootstrap. |
| `signing_key_id` | Exact signed key identifier. |
| `approved_account_sid` | Exact signed Trading SID, reconciled with the resolved local SID. |
| `provider_id` | Exact signed/public approved provider identifier. |
| `permitted_provider_operation` | Exact signed/public approved operation. |
| `authority_policy_version` | Exact supported value `authority-policy/v1`. |
| `claim_policy_version` | Exact supported value `claim-policy/v1`. |
| `created_at_utc` | Local administrator initialization evidence in Architecture-77 timestamp v1. It is not an identity input. |
| `bootstrap_digest` | 32 raw bytes equal to SHA-256 of the exact canonical signed bootstrap bytes. |
| `database_identity_digest` | 32 raw bytes equal to the signed bootstrap identity value. |
| `metadata_json` | Exact canonical `authority-metadata/v1` UTF-8 bytes defined below. |
| `metadata_digest` | 32 raw bytes equal to SHA-256 of `metadata_json`. |
| `production_schema_id` | Exact `windows-transactional-authority-schema/v1`. |
| `production_schema_version` | Integer, exact `1`. |
| `production_schema_digest` | 32 raw bytes equal to the SHA-256 of the exact packaged SQL artifact. |
| `metadata_encoding_version` | Exact `authority-metadata/v1`. |
| `initialization_policy_version` | Exact `authority-initialization/v1`, identifying this approved one-transaction initialization procedure. |
| `singleton_key` | Integer, exact `1`; the singleton fence. |

The five added fields are not decorative duplicates. The schema ID/version and
artifact digest identify the exact DDL; the metadata encoding version fixes
the bytes used by the metadata digest; and the initialization policy version
prevents a future initializer with different transaction or authority rules
from being treated as the same initialization evidence.

The columns that duplicate bootstrap and schema facts are deliberate typed,
queryable projections of the canonical metadata object. The validator requires
column-to-object equality, so a caller cannot alter a column without also
creating a new invalid metadata byte sequence and digest.

## 4. Canonical metadata semantics

### 4.1 Exact object and encoding

`metadata_json` is the exact `authority-metadata/v1` semantic object. Its key
set is exactly:

```text
approved_account_sid
authority_epoch_id
authority_policy_version
bootstrap_digest
bootstrap_generation
bootstrap_schema
claim_policy_version
created_at_utc
database_identity_digest
initialization_policy_version
machine_authority_id
metadata_encoding_version
production_schema_digest
production_schema_id
production_schema_version
provider_id
permitted_provider_operation
signing_key_id
singleton_key
```

The object is one flat JSON object. Its values are exact JSON strings except
for `bootstrap_generation`, `bootstrap_schema`, `production_schema_version`,
and `singleton_key`, which are exact JSON integers. Booleans, nulls, arrays,
objects, and floating-point values are not accepted anywhere.

The canonical bytes use the repository's established bootstrap convention:

```python
json.dumps(
    object,
    ensure_ascii=False,
    sort_keys=True,
    separators=(",", ":"),
).encode("utf-8")
```

The implementation must parse with duplicate-key rejection, reject unknown or
missing keys, reject non-canonical JSON bytes, and require the generated bytes
to equal the stored bytes exactly. Key ordering is lexicographic and is not
dependent on dictionary insertion order. All accepted strings are ASCII under
the existing UUID, SID, key-ID, provider, operation, and policy contracts, but
UTF-8 and `ensure_ascii=False` remain explicit format rules.

UUID values are lowercase canonical UUID text. SHA-256 values in JSON are
lowercase 64-character hexadecimal text and are converted to/from exactly 32
raw bytes in SQLite. The timestamp is exactly Architecture-77 timestamp v1:
`YYYY-MM-DDTHH:MM:SSZ`, valid proleptic Gregorian date, no fractions, offsets,
leap seconds, or year zero.

`metadata_digest` is SHA-256 over the exact canonical UTF-8 bytes, not over a
re-serialized SQLite row, SQL text, or database file. The reviewed Python
initializer/service computes that digest before insertion and the read-only
validator recomputes it before authority use. SQLite v1 enforces the BLOB
length, NULL/NOT NULL, immutability, and row/state rules but does not call a
custom cryptographic function from a trigger or other persistent schema code.
Every other persisted evidence pair follows the same responsibility split.

### 4.2 Binding classes

The object makes the authority boundary explicit:

- **Signed bootstrap facts:** machine, epoch, generation, bootstrap schema,
  signing key, approved SID, provider, operation, authority policy, claim
  policy, and database identity. `bootstrap_digest` is derived from the exact
  signed canonical bytes and is not a substitute for signature verification.
- **Schema identity facts:** production schema ID/version/digest, metadata
  encoding version, and initialization policy version. These are code-owned
  reviewed facts, not administrator-editable values and not signed by the
  existing bootstrap schema.
- **Local initialization evidence:** `created_at_utc`, the metadata digest,
  and the initial migration evidence. The timestamp is recorded evidence, not
  trusted exchange time and not UUID5 identity material.

`database_path` and `output_root` are not copied into metadata. Architecture
78 independently verifies the fixed final paths, and the signed bootstrap
already owns those path facts. Duplicating them in an unsigned database row
would add no authority and would create another reconciliation surface.

## 5. Database identity and bootstrap reconciliation

### 5.1 Meaning of `database_identity_digest`

The value is an administrator-generated, random 256-bit authority identity.
It is not a hash of the SQLite file, journal, schema, metadata, or any other
bytes that contain the identity. The bootstrap-generation procedure obtains
exactly 32 bytes from the approved administrator CSPRNG, encodes them as
lowercase 64-character hexadecimal text in the bootstrap, and signs the
canonical bootstrap bytes. Initialization stores the same value as 32 raw
bytes in SQLite and lowercase hexadecimal in canonical metadata.

Comparison is exact byte equality after strict lowercase-hex parsing. The
identity participates in canonical metadata and therefore in
`metadata_digest`; it participates in the signed bootstrap digest by being a
bootstrap field; it does not participate in the SQL artifact digest or schema
manifest. No digest is computed over bytes that contain the identity, so there
is no circular digest.

A copied database from another bootstrap fails because its identity and other
metadata facts do not equal the newly verified signed bootstrap. A copied
Architecture-77 fixture fails because it has no production metadata/schema
identity contract. A complete same-generation database plus its persistent
journal, copied together and presented under the same bootstrap and fixed
paths, is not distinguishable from the original by database-local state. That
rollback/replacement case remains outside this boundary and requires the
Architecture-78/native administrator replacement, backup-manifest, and
generation/epoch controls. An approved restore uses a new signed generation
and epoch and a new empty executable database; old claims are never imported.

### 5.2 Exact post-signature reconciliation

After signature verification over the exact bytes read from the trusted
bootstrap handle, the initialized database must prove all of the following
equalities:

| Database fact | Required value |
| --- | --- |
| `machine_authority_id` | Verified bootstrap machine ID. |
| `authority_epoch_id` | Verified bootstrap epoch ID. |
| `bootstrap_generation` | Verified bootstrap generation. |
| `bootstrap_schema` | Verified bootstrap schema, exactly 1. |
| `signing_key_id` | Verified bootstrap key ID. |
| `approved_account_sid` | Verified bootstrap SID and the actual resolved Trading SID. |
| `provider_id` | Verified bootstrap/public descriptor provider. |
| `permitted_provider_operation` | Verified bootstrap/public descriptor operation. |
| `authority_policy_version` | Verified bootstrap policy, exactly `authority-policy/v1`. |
| `claim_policy_version` | Verified bootstrap policy, exactly `claim-policy/v1`. |
| `database_identity_digest` | Exact 32-byte representation of the verified bootstrap value. |
| `bootstrap_digest` | SHA-256 of the exact canonical bootstrap bytes that were signature-verified. |
| `production_schema_id/version` | Code-owned v1 constants. |
| `production_schema_digest` | SHA-256 of the exact code-owned SQL artifact. |
| `metadata_encoding_version` | Code-owned `authority-metadata/v1`. |
| `initialization_policy_version` | Code-owned `authority-initialization/v1`. |

The validator also requires canonical metadata bytes/digest, exactly one
singleton row, exactly one v1 migration row for the epoch, and no other
application schema objects beyond the exact manifest. A valid row with a
different bootstrap digest, provider, policy, epoch, machine, generation,
SID, signing key, or identity is a mismatch, not a repair candidate.

The bootstrap digest, metadata digest, migration digest, release-manifest
digest, and every Architecture-77 evidence-pair digest are recomputed in
Python over the exact stored BLOB bytes. A mismatch is rejected before any
dependent authority mutation. No digest is accepted merely because its BLOB
length is 32.

## 6. Version and migration contract

Production supports exactly one executable schema version: integer `1`.
There is no startup upgrade, downgrade, `ALTER` repair, or migration engine.
Unknown, old, or future versions fail closed. `schema_migrations` is an
append-only historical evidence table; its rows do not authorize DDL.

The initialization transaction creates the v1 schema and then inserts exactly
one initial row whose meaning is “the reviewed v1 production artifact was
initialized for this exact authority epoch.” It is not a record that a
runtime migration ran.

The row contract is:

- `migration_id` is deterministic `migration_id/v1` UUID5 over
  `authority_epoch_id`, schema version `1`, and
  `migration_policy_version` using Architecture-77 framing;
- `authority_epoch_id` equals the metadata epoch;
- `schema_version` is exactly `1`;
- `migration_policy_version` is exactly `migration-policy/v1`;
- `migration_digest` is SHA-256 of exact canonical `migration_json` bytes;
- `application_release_digest` is the raw SHA-256 of the code-owned
  `authority-initializer-release-manifest/v1` resource at
  `src/trading_bot/runtime/schema/authority_initializer_release_manifest_v1.json`.
  That manifest is canonical UTF-8 JSON with the exact flat keys
  `application_version`, `initializer_contract_version`, `manifest_id`,
  `production_schema_digest`, and `production_schema_id`; all values are
  strings, `manifest_id` is exactly `authority-initializer-release-manifest/v1`,
  `initializer_contract_version` is exactly `authority-initializer/v1`, and
  the schema fields equal the v1 artifact constants. It contains no clock,
  path alias, secret, or self-digest. The release digest is forensic
  initializer provenance, not a bootstrap fact or permission to migrate. The
  approved release manifest digest is code-owned; an arbitrary 32-byte value
  is not accepted by the validator;
- `applied_at_utc` is administrator initialization evidence in timestamp v1;
  it is not in the UUID5 tuple; and
- update and delete are rejected by triggers. A second row for the same
  epoch/version is rejected by the unique constraint.

`migration_json` has the exact flat key set:

```text
application_release_digest
applied_at_utc
authority_epoch_id
initialization_policy_version
migration_id
migration_policy_version
production_schema_digest
production_schema_id
schema_version
```

It uses the same canonical JSON rules as metadata. The digest hex in the JSON
must equal the `application_release_digest` BLOB column; all other values
must equal their corresponding row or code-owned v1 constant. The migration
row is therefore self-consistent without introducing a database-file digest.

If a future schema needs a new DDL, trigger, policy, or migration meaning, it
requires a separately reviewed artifact identity and explicit implementation
milestone. It may not alter v1 on startup or reinterpret the v1 row.

## 7. Initialization authority and CLI boundary

Initialization is a separate explicit elevated-administrator action:

```text
windows-authority initialize-database
```

The exact command name is part of the implementation contract; it is not a
new mode of normal `validate`, and it is not silently appended to
`provision`. The existing `provision` command installs/validates trust
material and leaves database schema creation deferred. The new action may be
implemented in the existing administrator CLI and may call a distinct
internal initializer API, but the authority boundary must remain explicit.

Before opening a writable SQLite connection, the command must require:

1. an elevated administrator token;
2. the fixed parent/root/database/journal final-path and security checks;
3. the real local Trading SID and exact equality with the signed bootstrap;
4. valid pinned-key/signature/bootstrap/policy verification;
5. a complete pre-created database/journal pair;
6. the approved release manifest and SQLite build manifest, including the
   exact VFS name to bind at open; and
7. the exact `PRECREATED_UNINITIALIZED` state.

The Trading account cannot initialize the schema. Normal `validate` never
initializes. An already `INITIALIZED_SUPPORTED` exact database is accepted as
an idempotent no-op; a mismatched, partial, old, future, corrupt, or hostile
initialized database is never modified into compliance.

The initializer must use the fixed code-owned path after final-handle
validation. It cannot accept a database path, schema path, output path,
identity, epoch, SID, or policy from CLI arguments or environment variables.
Production initialization, installed validation, and provisioning also cannot
accept caller-supplied key registries, release manifests, SQLite build
manifests, or timestamps. Those values come only from the production-pinned
registry, approved resources, and the internal UTC clock. Disposable tests
use separately named injection boundaries.

## 8. Transactional initialization sequence

The initializer owns its exact `sqlite3.Connection`; it rejects an active
transaction before any setup and does not accept a caller-owned transaction.
The sequence is:

1. Complete Architecture-78 filesystem/bootstrap/SID validation and retain
   the verified bootstrap facts. Resolve and validate the fixed database and
   journal handles before opening SQLite.
2. Open the exact fixed database with `mode=rw&vfs=<approved-vfs>` and
   `uri=True`; there is no URI fallback or create fallback. Immediately
   require one `main` database at the exact fixed path, no attachments, and
   the pre-created persistent journal.
3. Establish `trusted_schema=OFF` using the public Python 3.12+ standard
   library configuration path where available, then read back
   `PRAGMA trusted_schema` and require `0`. If the setting cannot be
   established or read back, stop without DDL.
4. With no active transaction, request `PRAGMA foreign_keys=ON`,
   `PRAGMA journal_mode=PERSIST`, and `PRAGMA synchronous=FULL`; read each
   value back and require `1`, `persist`, and `2`. Recheck the database list,
   trusted-schema setting, and persistent journal after the PRAGMAs. These
   connection setup writes occur before the schema transaction and are
   connection-local security/durability setup, not schema initialization.
5. Read the schema and integrity in the current connection. If it is not
   exactly empty of application objects, classify it before DDL; do not run
   repair DDL. Internal SQLite objects alone are the only allowed pre-created
   content.
6. Capture and validate `created_at_utc`, `applied_at_utc`, and the approved
   release-manifest digest before beginning the transaction. No clock, file,
   provider, credential, or external process call is made while the SQLite
   transaction is open.
7. Execute `BEGIN EXCLUSIVE`. The initializer uses EXCLUSIVE for this
   one-time schema boundary so no concurrent reader can observe a partially
   materialized schema and no competing initializer can pass the preflight.
   Normal Architecture-77 runtime writes continue to use `BEGIN IMMEDIATE`.
8. Execute every statement from the canonical artifact in order while this
   transaction remains active. The implementation must not use Python
   `executescript`, because its implicit pre-script commit would break the
   all-or-nothing contract. It must use a reviewed complete-statement runner
   or equivalent statement list that does not commit between DDL statements.
   The artifact must execute successfully with `trusted_schema=OFF` and with
   no application-defined SQL functions registered.
9. Compare the in-transaction schema manifest to the expected materialization.
   The Python service computes and verifies canonical metadata and migration
   bytes/digests, then inserts the exact immutable `authority_metadata` row and
   initial `schema_migrations` row. It computes all other new evidence-pair
   digests before their reviewed insert/update statements; SQLite does not
   recompute any of them.
10. Before commit, verify singleton counts, row-to-object equality, all
    Python-recomputed content digests, exact schema/version/policy values,
    foreign-key checks, and `PRAGMA integrity_check`. Where practical,
    exercise immutable and no-delete trigger paths inside savepoints and roll
    those probes back; no probe result may be used to repair the authority.
11. Commit. The metadata row, migration row, all DDL, indexes, and triggers
    become one durable SQLite commit. No external side effect is performed
    while the transaction is open.
12. Close the connection, revalidate the fixed final path and journal, reopen
    the database with `mode=ro&vfs=<approved-vfs>` and `uri=True`, and run the
    complete installed validator. Report success only if it returns
    `INITIALIZED_SUPPORTED` for the same signed bootstrap and exact production
    schema.

SQLite ordinary CREATE TABLE, CREATE INDEX, and CREATE TRIGGER DDL
participates in the surrounding transaction. A rollback therefore removes
the schema objects and initial rows together. This contract does not rely on
`VACUUM`, WAL, implicit commits, or a Python script convenience API.

`PERSIST` and `FULL` are requested and read back, but their values alone do
not prove abrupt-power-loss durability. Native SQLite version, VFS, Windows
NTFS behavior, locking, flush semantics, and the persistent-journal rights
still require the production acceptance described below.

## 9. Crash, retry, and journal semantics

| Interruption point | Required next-state interpretation |
| --- | --- |
| Before `BEGIN EXCLUSIVE` | No accepted schema change. A retry re-runs all trust and storage checks. |
| During DDL | SQLite transaction rollback is expected to return the pair to `PRECREATED_UNINITIALIZED`; if reopen shows partial objects, corruption, or uncertainty, fail closed for manual investigation. |
| After some DDL and before commit | Same rollback expectation; never execute repair DDL over a partial state. |
| After metadata insertion and before commit | Metadata and schema_migrations are uncommitted and must roll back with the DDL; a partial durable row is not repaired. |
| After COMMIT but before CLI success | Reopen and validate. An exact same-bootstrap/schema result is `INITIALIZED_SUPPORTED` and retry is an idempotent no-op. |
| Persistent journal residue after restart | The journal is retained and required. SQLite may recover an uncommitted transaction during open; accept only the resulting exact empty or exact supported state after integrity and manifest validation. Any corruption or ambiguous partial state fails closed. |

SQLite transactional DDL and rollback journaling provide the expected
before-commit atomicity when the reviewed native build and filesystem honor
their contract. `PERSIST`/`FULL` do not by themselves guarantee every
abrupt-power-loss outcome; that is an operational acceptance claim, not a
property inferred from a PRAGMA readback.

Initialization is idempotent only for an already fully validated exact
`INITIALIZED_SUPPORTED` database with the same signed bootstrap, database
identity, artifact digest, metadata bytes, and migration evidence. It does not
insert a second row, refresh timestamps, or rewrite any bytes. A database with
different signed facts, schema, metadata, migration evidence, or release
policy is never changed.

## 10. Database state model and command acceptance

The production state model is:

| State | Meaning | `validate` | `provision` | `initialize-database` | runtime open |
| --- | --- | --- | --- | --- | --- |
| `NOT_PRESENT` | Neither fixed database nor journal exists. | Report only. | May preserve this deferred state. | Reject; administrator must pre-create the pair first. | Reject. |
| `PRECREATED_UNINITIALIZED` | Paired, structurally valid database/journal with no application objects. | Report only. | Preserve and report. | Accept as the only new-initialization input. | Reject. |
| `INITIALIZED_SUPPORTED` | Exact v1 schema, exact immutable evidence, exact bootstrap binding, and integrity all pass. | Accept read-only. | Accept only as an exact idempotent installed state. | Accept only as an exact no-op. | Accept after the future runtime setup gate. |
| `INITIALIZED_UNSUPPORTED` | Valid SQLite with application objects, but exact approved v1 schema/identity cannot be proven: old/future/partial schema, copied Architecture-77 fixture, metadata-only state, extra object, missing object, or changed trigger/constraint. | Fail closed. | Fail closed. | Reject without mutation. | Reject. |
| `INVALID_MISMATCHED` | Incomplete pair, corrupt pages, failed integrity/foreign-key/path/attachment checks, or production-looking metadata that does not reconcile with the verified bootstrap or canonical bytes. | Fail closed. | Fail closed. | Reject without mutation. | Reject. |

The state is evidence, not a caller-selected mode. A database is never
promoted from unsupported or mismatched to supported by deleting rows, adding
missing DDL, rewriting metadata, clearing a journal, or changing the
bootstrap. Manual recovery provisions a new signed generation/epoch and new
empty database.

## 11. Future installed-validation evidence

The implementation should return a public immutable typed evidence object
whose fields are limited to sanitized authority facts, including:

- state and fixed database/journal paths;
- machine/epoch/generation and approved SID;
- provider/operation and supported policy versions;
- bootstrap digest and database identity digest;
- production schema ID/version/artifact digest;
- metadata encoding and initialization policy versions; and
- migration ID/schema version/application release digest.

It must not return raw SQL, arbitrary JSON, provider bodies, credentials,
private keys, environment dumps, stdout/stderr, or native exception text.

The read-only validator specifically does not configure writable PRAGMAs. It
must prove the fixed filesystem and signed bootstrap first, then prove SQLite
scope/integrity/schema/metadata/migration/binding, and only then produce this
evidence. A failed validator leaves the database untouched.

## 12. Future runtime-open gate

Architecture-77 runtime services must not accept an arbitrary SQLite
connection. They should receive an immutable
`ValidatedProductionAuthority` value produced by the installed validator,
containing the exact bootstrap-bound facts and database identity. A separate
runtime connection factory then:

1. verifies that the evidence is fresh for the same fixed deployment and has
   not been substituted by caller fields;
2. opens only the fixed database and confirms one main database/no ATTACH;
3. establishes and reads back `trusted_schema=OFF` before preparing or
   executing persistent schema-controlled SQL;
4. requests and reads back `foreign_keys=ON`, `journal_mode=PERSIST`, and
   `synchronous=FULL` on the writable connection;
5. retains the exact database identity in the authority context; and
6. refuses all session, attempt, claim, reservation, or recovery mutation
   until the supported schema/policy gate has passed.

The context object is evidence, not a replacement for the OS lifecycle
arbiter. External provider/process boundaries still follow Architecture-77:
no SQLite transaction across an external call, committed intent before a
call, exact typed result, and conservative recovery after uncertainty.

## 15. Adversarial design review

- **Digest circularity:** schema digest hashes only packaged SQL; database
  identity is random and does not hash database bytes; metadata/migration
  digests hash their own canonical bytes only.
- **Redundant or unbound metadata:** duplicated columns are projections of the
  canonical metadata object and are compared both to it and to the signed
  bootstrap. Paths remain owned by Architecture 78 instead of being copied
  into an unsigned row.
- **Fingerprint ambiguity:** artifact digest plus exact materialized manifest
  checks SQL text, tables, columns, indexes, foreign keys, triggers, and
  CHECK expressions; root pages are excluded intentionally. A different
  SQLite materialization fails closed.
- **SQLite-version dependence:** the validator and package are tied to a
  reviewed native build. It does not broaden comparisons to accommodate an
  unapproved version.
- **Rollback/replay:** before-commit work is one SQLite transaction; after
  commit exact validation is idempotent; mismatches are never repaired or
  replayed. Same-generation complete database replacement remains the stated
  external trust-boundary limitation.
- **Partial/copied databases:** only an empty paired database may be newly
  initialized; all partial, copied, old, future, or foreign states fail
  closed.
- **Automatic repair:** none exists in validation, provisioning,
  initialization retry, or runtime open.
- **Migration ambiguity:** v1 has one historical initialization row and no
  migration engine. Future schema changes require a new reviewed artifact and
  milestone.
- **Administrator versus Trading:** initialization requires elevated admin;
  Trading only consumes a fully validated authority. The signed SID is still
  verified before either path reaches SQLite.
- **Path ordering:** fixed final-handle and bootstrap trust precede SQLite
  open; the SQLite URI cannot select an alternate path.
- **Validation mutation:** installed validation is `mode=ro` and never writes
  PRAGMAs, DDL, metadata, or journal bytes.
- **Connection assumptions:** every production connection establishes and
  reads back `trusted_schema=OFF`; writable connections additionally read back
  all three durability settings and prove one main database. No custom SQL
  hash function is registered or required.
- **Artifact/fixture divergence:** the package artifact is the only full SQL
  source; the former fixture copy is absent, and the executable harness has a
  byte-equality regression against the public package resource.

No security-relevant schema choice is intentionally left ambiguous. The
approved native SQLite/VFS/trusted-schema build, production trust anchor, and
release manifest are external acceptance inputs that must be supplied before
GO; a production UDF build is not required.
